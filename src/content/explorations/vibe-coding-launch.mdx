## 安装环境

**🎯 阶段目标**：在自己电脑上把代码环境跑起来。环境配置只在首次需要，之后每次开发直接打开项目即可。

### 权限与账号准备（两条实践线通用）

1. **申请仓库与网络权限**：向项目管理员申请代码仓库访问权限；如项目需要专用网络或测试环境权限，按团队流程申请。

2. **确认 Git 已安装**：在终端输入 `git --version`；若提示 `command not found: git`，执行 `xcode-select --install` 安装。

3. **登录代码平台**：按照所使用的代码托管平台要求完成账号登录或身份认证。

4. **生成并配置 SSH Key**：

   - 生成密钥 `ssh-keygen -t rsa -b 4096 -C 'youremail@example.com'` 过程中一直按回车，不需要设置密码。

   - 复制公钥 `pbcopy < ~/.ssh/id_rsa.pub`

   - 进入 代码托管平台的「SSH Keys」设置页，点「New SSH key」粘贴保存；

   - 验证连接 `ssh -T git@<代码托管平台域名>` 首次提示输入 `yes`。若返回认证成功提示，继续下一步。

   - 设置 Git 身份 `git config --global user.email youremail@example.com`

也可以直接让 AI Agent 帮忙生成 SSH Key、打印公钥；但公钥仍需手动到代码平台的 SSH Keys 设置页上传，完成完整认证。若 AI 在沙箱内写 `~/.ssh` 目录报错，选择「在沙箱外运行」即可。

### Web 前端环境（网页项目）

适用在研发同仓库上新建分支做设计原型、或直接打磨线上样式的场景。具体仓库地址由项目维护者提供。

1. **克隆代码到本地**，拉取过程通常较慢。 `git clone <仓库 SSH 地址>`

2. **初始化项目**：拉取完成后，在 IDE 中让 AI 按项目 README\.md 初始化环境（涉及安装全局工具、Node\.js 等）。注意口令要说清「帮我按照 README\.md 初始化」，只说「读一下 readme」AI 不会主动安装。初始化过程若出现报错、AI 没做完，可找研发同学在终端手动执行命令完成，通常约 10 分钟。

3. **配置预览环境认证**：按照项目文档完成测试环境登录与权限配置；如需本地环境变量，在 IDE 中找到项目对应的 `.env.local` 文件，按文档填写配置（不要将 Cookie 或密钥直接发送给 AI）。

4. **安装依赖并启动**：

   - 新建分支后先执行 `rush update` 安装依赖；环境异常时可用 `rush update --purge` 重置依赖；

   - 进入对应应用目录（如 `apps/<应用目录>`）执行 `pnpm dev`；控制台出现绿色文字即启动成功，打开对应预览环境即可预览。

### 移动端环境（iOS \+ Android 双端）

移动端项目依托独立客户端开发环境，可输出高保真 Demo，并同时产出 iOS 与 Android 双端可交付代码，适合独立的新功能、新页面场景。手动安装预计耗时约 1 小时。

## Coding 实践

**🎯 阶段目标**：在 Agent 中用自然语言把设计稿 / 想法做成可运行的 Demo，并反复调到还原。核心能力是审美判断力和描述能力，不需要会写代码。

### 启动项目并确认分支

- 用 AI Agent 工具打开项目文件夹：双端打开 `<项目根目录>` 根目录，单端打开对应端目录；Web 项目打开克隆下来的仓库目录。

- 用 Xcode / Android Studio 分别打开对应端目录并启动模拟器；Web 项目执行 `pnpm dev` 本地预览。

- 向 Agent 发送指令创建新分支，如「基于 main 分支为新项目创建 demo/Yourproject 分支」，也可手动创建。做修改前先确认当前分支名：Agent 工具内的分支视窗可查看；Trae 不展示分支名时直接问它「当前我所在的分支是什么」；Xcode 与 Android Studio 在页面顶部展示分支。

### 用自然语言做 Demo

以还原 Figma 设计稿为例，向 Agent 发送还原要求，可附上设计稿 MCP 链接、页面截图或素材图片。以移动端页面为例：在 `Project_iOS` 和 `Project_Android` 下的示例目录各新建一个叫做 ExamplePage 的文件夹；使用 项目 Design System 帮我做这个 ExamplePage 面板，要求百分百还原设计稿。

- 确保 AI 通过 MCP 成功读取到设计页面，并阅读到 `claude.md` 和项目 Skills，避免 AI 忽略设计规范。

- 告诉 AI 在当前分支下操作，否则它可能自动新建分支；创建新项目时明确给出新项目名称，避免随机命名。

- AI 输出结束后一轮还原完成，打开编译器 / 本地预览查看效果。

### 细节调整与预览

第一轮还原通常会有不少细节问题，继续与 AI 沟通修正：多个细节问题尽量一次性把修改点全部喂给 AI——AI 擅长并行任务，能 spawn 多个子任务分别执行，一次提 10 个修改点比分 10 次提高效得多。

- **图标还原有误**：在开发模式下找到正确的 icon token（如 `Icon/Example_Icon`），把 token 描述给 AI 让其还原；项目图标库可右键复制 React 代码交给 AI 替换，其余图标库可用「库名 \+ 图标名」方式替换。

- **图片与圆角还原有误**：到 Figma 开发模式选中对应图层，下载 jpg / png 素材，再告诉 AI「第一个 single clip 的图片请使用给你的图 1 还原，所有 single clip 圆角为 16」。

- **精调定位**：使用 UI 元素选择功能（放大镜）钻入对应元素，复制其命名、大小、边距等描述给 AI，方便 AI 定位改动；也可借 IDE 自带的 GUI 点选功能调整，改完记得点 Apply 应用。

- **预览查看**：iOS 点 Xcode 左上角小三角运行模拟器；Android 点 Android Studio 上方绿色三角运行模拟器；Web 在预览环境刷新页面查看。

### 后续拉取最新仓库

仓库代码会持续更新（更新组件、修复历史 Bug），再次打开项目或创建新项目前建议拉取最新代码：

1. 切换到 main 分支；

2. 跟 AI 说「帮我拉取最新的 main」，AI 会自动同步；

3. 基于最新的 main 创建新分支再开始做新项目；

4. 老项目基于旧版 main 时，可让 AI「把最新 main 合并到我当前分支」；若双方改了同一位置出现冲突提示，不要硬改，先让 AI 或开发同事协助处理。

## 发版流程

**🎯 阶段目标**：把本地改动提交到远程仓库，经研发 Code Review 后合入主干、按项目流程上线。移动端做普通 Demo 项目时建议仅 Push，不把临时代码合入 Main；仅可复用模块（可复用动画、视觉资源）在打磨确认无 Bug 后再合入。

### 本地提交（Commit）

- 向 Agent 发送指令 `Commit`，或使用 Agent 自带的提交功能，把当前改动在本地保存成一个版本记录。

- 准备合并到 master 前，可直接对 Agent 说：**「帮我给当前的分支 rebase 一下远程的 master 分支，然后再提交上去」**。rebase（变基）会把当前分支的提交移动并重新应用到目标分支最新提交之上，让提交历史保持线性、无分叉。

### 推送远端（Push）

向 Agent 发送指令 `Push 并给我对应的远端分支链接`，或使用自带推送功能。Push 会把本地已 commit 的版本上传到远程仓库；只说「Push」时，Agent 可能直接给出提交 MR 的链接。

- 推送前若提示识别不到用户身份，到代码托管平台的个人设置中查看用户名与邮箱，把对应信息配置给 AI，在项目根目录执行 `git config user.email`、`git config user.name` 即可。

- Push 后拿到远端分支链接，可先发给对应研发知悉。

### 部署预览环境（Preview Deployment）

本地改动默认只在本机可见；需要给他人查看效果时，部署到预览环境：

1. 提交代码并推送到远程分支；

2. 打开项目对应的 预览环境部署流水线（链接需单独申请权限）；

3. 点右上角「运行」，填入自己的分支名，定义一个预览环境名称，等待部署完成；

4. 部署好后访问对应预览环境即可看到改动；没改好就重复 Coding → Commit → 运行部署的步骤。

如果项目配置了自动部署流水线，关联分支有代码更新时，流水线可自动执行并更新预览环境。

### 创建开发任务与代码评审（Code Review）

1. 进入项目代码管理平台创建开发任务，完成基础配置：选择对应开发流程；任务概述可加 UX 前缀与技术需求区分；选择对应项目名称；开发分支选自己的分支，目标分支选 master。具体配置建议先与本团队研发同学确认。

2. 页面会进行代码准出检测；开发进度完成后点「完成开发」，代码合入目标分支。代码评审描述内可填写关联的预览环境信息。

3. 评审出现报错冲突时，把平台返回的报错信息截图交给 AI 快速修正，再重新提交；只要代码分支未修改，提交后都会重新走代码评审流程。

4. 开发任务合入 master 后，获取【代码评审】页面链接，联系对应评审人进行 CR，参考格式：改动点说明 \+ 关联开发任务 \+ @评审人。

### 按评审意见修改并合入发布分支（Release Merge）

1. 研发给出修改建议后，回到分支按反馈重新修改；代码分支未改动时，保存提交后自动重新走评审流程；若新建了代码分支则需换到最新分支。

2. 开发任务完成后，系统会自动创建一条到发布分支的新 MR（没有系统推送）；进入平台 MR 列表找到这条消息，点 **Rebase and merge** 即可。

3. 按照团队的发布流程登记本次上线需求与 MR 链接；尽量在发布截止前完成代码合入，方便 QA 介入回归验证。

### 漏合入发布分支时的补救（Cherry\-pick）

如果忘记手动合入发布分支，代码可能没有跟随上一版发布上线。先在代码管理平台找到遗漏的改动，重新提交，并把对应的 MR 链接和需要补入的提交记录发给研发；再由研发将这些提交 **Cherry-pick** 到最新发布分支。

Cherry\-pick 是 Git 里精准复制某一个提交（commit）粘贴到另一个分支的命令：普通 merge 是把整个分支合并过来（一锅端），cherry\-pick 是只挑一个 / 几个提交单独拿过来（精挑细选）。

## Coding 实践 Tips

#### 01. 提前明确代码规范，避免 AI 自由发挥

Coding 前先与 RD 确认团队的技术约束，例如只能新增 Swift 代码、不能新增 Objective-C 代码，以及组件复用和命名要求，并明确告诉 Agent。否则 AI 可能生成不符合仓库规范的代码，增加后续 MR 修改成本。

#### 02. 提前划定改动范围，避免误改复杂业务逻辑

开始前明确本次只修改 UI 样式、简单交互，还是允许调整业务逻辑。对于耦合复杂或不在本次需求内的模块，直接标明不允许修改，避免 AI 扩大改动范围、反复试错。

#### 03. 先理解技术实现，再处理复杂问题

遇到布局适配或交互异常时，先让 Agent 分析当前架构、布局锚点、已有组件及可调参数，再决定最小修改方案。这样比直接要求 AI 不断修复更容易命中问题，也能减少对既有框架的破坏。

#### 04. 提前定位代码文件路径，减少无效搜索与 Token 消耗

大型仓库中，尽量提前提供对应页面、组件和逻辑文件的位置。让 Agent 从相关目录开始分析，而不是遍历整个项目，可以减少无关上下文和重复检索。

#### 05. 提前整理 Figma 图层，提高 AI 还原准确率

使用 Figma MCP 读取设计稿前，清理无用的隐藏图层、规范图层命名，并整理必要的层级和组件关系。结构清晰的设计文件有助于 Agent 更准确地理解界面，减少还原时的猜测。

#### 06. 尽量使用设计 Token，避免大量硬编码

AI 生成的颜色、字号、圆角和间距可能直接写成固定数值。合码前应尽量映射到项目已有的 Design Token，避免同类样式在多个文件里重复定义；可借助 Tailwind CSS IntelliSense 辅助检查样式配置。

#### 07. 将交互逻辑与视觉表现解耦，降低调试复杂度

不要一开始就要求 AI 同时完成复杂逻辑和所有视觉细节。可以先做主 UI、再按模块叠加交互；也可以先跑通纯逻辑版本、再补齐样式，让问题更容易隔离和验证。

#### 08. 完成一个功能闭环就提交一次 Commit

每完成一个相对独立且验证通过的能力，就及时创建 Git Commit。清晰的提交记录有利于定位问题、比较修改，也便于必要时恢复到稳定版本。

#### 09. 截图无法识别时，先检查模型的视觉能力

如果 Agent 无法理解截图，先确认所用模型和当前工具是否支持图片输入。遇到模型或入口能力限制时，可切换到支持视觉理解的模型，而不是在同一限制下反复修改 Prompt。

#### 10. 确认实际预览地址，避免在错误页面上调试

本地默认端口可能被占用，例如应用从 `3000` 自动切换到 `3001`。切换工具或重启服务后，及时核对真实预览地址，并让 Agent 基于当前实际运行的页面验证修改。

#### 11. 提交前核对变更文件，避免漏提或错提

本地运行正常，不代表所有相关文件都已加入 Git 提交。提交前让 Agent 检查 `git status` 与代码差异，核对必需文件、排除无关改动和敏感配置，避免预览环境出现缺失修改的情况。

#### 12. 按页面或功能模块拆分 MR，降低 Review 成本

与 RD 交付代码时，尽量围绕独立页面或功能拆分 MR，避免将多个不相关需求混入一次合并。这样更方便 Review、测试、定位问题和按需回滚；如果功能跨页面强耦合，则按完整功能边界拆分。

#### 13. 发生代码冲突时，先定位原因再让 AI 协助处理

合并主分支或发布分支遇到冲突时，先让 Agent 识别冲突文件并解释双方修改，再处理简单的样式或独立逻辑冲突。涉及核心业务规则或架构的冲突，应由相关开发人员共同确认，避免直接覆盖有效代码。

#### 14. 根据交付目标选择落地模式

- 输出设计原型。 中小规模迭代可以在研发仓库申请权限，另建分支开发，代码可直接交付研发。只需展示的项目，可以将页面做成静态原型并通过 CDN 分享。
- 样式开发与研发并行。 研发主导功能开发，设计师参与交互评审，并独立完成视觉还原和样式调整，由研发评审代码。遇到样式冲突或复杂逻辑时，设计师先定位问题，再请研发协助。
- 独立发版打磨线上体验。 样式微调和不涉及功能变更的体验修复，可以由设计师直接改代码、本地验证、提交并参与发版。开始前先与研发确认团队的上线流程。
